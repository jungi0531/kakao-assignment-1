2. Todo CRUD

원본 Todo 배열은 App, 입력 draft와 편집 draft는 사용하는 컴포넌트 가까이에 둡니다.

Vanilla JS

  • 전역 배열을 직접 변경
  • renderTodos()를 수동 호출
  • DOM 요소를 직접 생성·교체
→

현재 React 코드

  • setTodos로 새 배열 생성
  • state 변경이 자동 리렌더 유발
  • isEditing으로 JSX 분기

state 위치가 핵심

  • todos: 모든 목록이 공유하므로 App
  • editingId: 한 번에 하나만 편집하므로 App
  • inputText: TodoInput만 사용하므로 TodoInput
  • editText: 개별 TodoItem의 draft이므로 TodoItem

불변성 규칙

// 추가
[...previousTodos, newTodo]

// 수정·완료
previousTodos.map(todo =>
  todo.id === id ? { ...todo, text } : todo
)

// 삭제
previousTodos.filter(todo => todo.id !== id)
이미 보완된 오류 한글 IME 조합 중 Enter 제출 방지, 빈 입력 재포커스, Escape 편집 취소, 편집 input 커서를 끝으로 이동, 100자 제한이 구현되고 테스트됩니다.

직접 수정: Todo 추가 로직 완성

핵심

기존 배열을 직접 수정하지 않고 새 배열을 만들어야 합니다.

함수형 업데이트에서 이전 배열을 받아 spread로 새 배열을 만드세요.
setTodos((previousTodos) => [...previousTodos, newTodo])

생각나는 질문들

편집 중 임시 문자열은 해당 항목만 사용하는 로컬 관심사입니다. 반면 editingId는 여러 항목 중 하나만 편집되게 조정해야 해서 App이 소유합니다.

React는 state 참조 변경을 기준으로 갱신을 판단합니다. 기존 값을 직접 수정하면 변경 추적과 이전 state 보존이 깨질 수 있어 새 배열과 새 객체를 만듭니다.

3. 상태별 필터링

필터 결과를 state로 복제하지 않고 원본 state에서 계산합니다.

원본 state

todos와 filter만 저장합니다.

필터링된 배열은 원본이 바뀌면 다시 계산할 수 있으므로 별도 state가 아닙니다.

파생값

const filteredTodos = useMemo(() => {
  if (filter === FILTER.ACTIVE) {
    return todosForDate.filter(todo => !todo.completed)
  }
  if (filter === FILTER.COMPLETED) {
    return todosForDate.filter(todo => todo.completed)
  }
  return todosForDate
}, [todosForDate, filter])
필터가 바뀌면 왜 목록이 다시 그려질까? setFilter → App 리렌더 → filteredTodos 재계산 → TodoList가 새 배열 props를 받기 때문입니다. DOM을 직접 숨기지 않습니다.
세밀한 포인트 필터 전환 시 editingId를 초기화합니다. 편집 중인 항목이 필터 결과에서 사라질 때 편집 대상 ID만 App에 남는 고아 상태를 막기 위해서입니다.

직접 수정: 진행 중 필터 완성

기초

배열의 filter와 boolean 부정 연산자를 사용합니다.
return todosForDate.filter((todo) => !todo.completed)

생각나는 질문들

todos와 filter에서 계산 가능한 값을 또 저장하면 원본 변경 때마다 동기화해야 합니다. 누락 시 화면과 원본이 불일치하므로 파생값으로 둡니다.

정확성을 위해 필수는 아닙니다. 현재 과제에서는 파생값임을 명확히 하고 반복 계산을 제한하는 목적으로 사용했습니다. 작은 배열에서는 성능 차이가 크지 않다는 점도 설명할 수 있어야 합니다.

4. Todo 일간 뷰

선택 날짜가 Todo의 생성 대상과 조회 조건을 동시에 결정합니다.

날짜 state

selectedDate는 Date 객체이며 App이 소유합니다.

const [selectedDate, setSelectedDate] =
  useState(loadSelectedDateFromStorage)

날짜별 Todo

Todo는 Date 객체가 아니라 YYYY-MM-DD 문자열을 저장합니다.

const todosForDate = todos.filter(
  todo => todo.date === getDateKey(selectedDate)
)

두 단계 파생 구조

전체 todos → 날짜 todosForDate → 완료 상태 filteredTodos → props TodoList

순서를 반대로 하더라도 결과는 만들 수 있지만, 현재 구조는 “날짜 화면 안에서 상태 필터를 적용한다”는 도메인 의미가 분명합니다.

이미 보완된 날짜 오류 new Date('YYYY-MM-DD')로 파싱하지 않고 연·월·일을 분리합니다. UTC 해석 때문에 한국 시간에서 전날로 보일 수 있는 문제를 피합니다.
날짜 이동 때 편집 상태를 닫는 이유 편집 중인 Todo가 이전 날짜 소속이면 새 날짜에서 컴포넌트가 사라집니다. editingId까지 초기화해야 다음에 돌아왔을 때 의도치 않게 편집 모드가 남지 않습니다.

직접 수정: 새 Todo의 날짜 연결

핵심

Date 객체 자체가 아니라 날짜 키를 저장합니다.
date: getDateKey(selectedDate),

생각나는 질문들

전체 Todo 배열 하나를 유지하면서 선택 날짜에 따라 조회하기 위해서입니다. 날짜별 배열을 여러 state로 나누지 않아 CRUD와 저장 계약이 단순해집니다.

기존 state 객체를 직접 변경하는 것이므로 참조가 유지됩니다. 먼저 복사한 새 Date를 수정한 뒤 반환해야 React가 명확하게 새 값으로 처리합니다.

5. localStorage

초기 복원은 lazy initializer, 이후 자동 저장은 Effect가 담당합니다.

Vanilla JS

추가·수정·완료·삭제 함수마다 saveTodos()를 직접 호출했습니다.

→

React

CRUD는 state만 바꾸고, useEffect([todos])가 최신 state를 저장합니다.

1. 최초 복원

const [todos, setTodos] =
  useState(loadTodosFromStorage)

함수 자체를 넘겨 마운트 초기값을 계산합니다. 컴포넌트 리렌더마다 storage를 읽지 않습니다.

2. 변경 후 저장

useEffect(() => {
  saveTodosToStorage(todos)
}, [todos])

todos 참조가 바뀐 commit 이후 최신 배열을 저장합니다.

storage.js가 복잡한 이유

localStorage의 문자열은 사용자가 개발자 도구로 바꿀 수 있고 이전 버전 데이터일 수도 있습니다. 따라서 JSON parse 성공만으로 신뢰하지 않습니다.

getItem → JSON.parse → 배열 확인 → 필드 검증 → ID 정규화·중복 제거
과제 최소 요구보다 강화된 부분 손상 JSON 폴백, Todo 필드 검증, 안전하지 않은 숫자 ID 거부, 숫자 1과 문자열 '1' 중복 처리, 읽기·쓰기 예외 허용, 날짜 범위 검증까지 포함합니다.

직접 수정: 자동 저장 Effect

필수 질문

Effect 안에서 읽는 reactive value는 의존성 배열에도 들어가야 합니다.
useEffect(() => {
  saveTodosToStorage(todos)
}, [todos])

반드시 설명할 수 있어야 하는 질문

괄호로 즉시 호출하면 컴포넌트 함수가 실행될 때마다 storage 읽기가 먼저 수행됩니다. 함수 자체를 넘기면 React가 초기 state가 필요할 때 initializer로 실행합니다.

마운트 뒤 한 번만 저장하므로 이후 CRUD 변경이 반영되지 않습니다. todos 변경을 감시해야 합니다.

브라우저 저장 공간이나 보안 정책 문제로 저장이 실패해도 현재 메모리 state와 UI 조작까지 중단시키지 않기 위해서입니다.

도전 미션. 주간 뷰

구현된 주간 뷰를 따라가며 두 날짜 state와 파생값의 연결을 확인합니다.

현재 구현 상태 DateNavigator를 WeekNavigator로 교체했고, 날짜 선택·주 이동·날짜별 Todo 개수·주 시작일 저장과 복원을 연결했습니다.

selectedDate

실제로 Todo를 추가하고 조회하는 대상 날짜입니다.

weekStartDate

화면에 보여줄 월요일부터 일요일 범위를 결정합니다.

두 state의 불변식

weekStartDate는 표시 주의 월요일
selectedDate는 표시 주간 7일 안에 포함
selectedDate는 Todo 입력·목록과 동일한 날짜
주 이동 시 둘 다 같은 방향으로 7일 이동

주 시작만 이동하면 화면은 다음 주인데 목록은 이전 주 selectedDate를 가리키는 불일치가 생깁니다.

직접 설계: 주 이동 후보 계산

도전

Date는 mutable이므로 두 state를 각각 복사한 새 객체가 필요합니다.
const nextWeekStart = createMidnightDate(weekStartDate)
nextWeekStart.setDate(nextWeekStart.getDate() + delta)

const nextSelectedDate = createMidnightDate(selectedDate)
nextSelectedDate.setDate(nextSelectedDate.getDate() + delta)

구현 후 설명할 수 있어야 하는 질문

현재 Todo 추가와 날짜 키 계산은 selectedDate가 항상 유효한 Date라는 계약을 사용합니다. null을 허용하면 입력 비활성화, 빈 목록 의미, storage 계약까지 모두 다시 설계해야 합니다.

필터 결과가 아닌 전체 todos에서 날짜별 개수 맵을 파생해야 합니다. 그래야 현재 선택 날짜와 필터에 상관없이 주간 7일의 전체 개수를 표시할 수 있습니다.

개념 질문

현재 공유 state는 todos, editingId, filter, selectedDate, weekStartDate 다섯 개이고 여러 자식이 함께 사용합니다. 규모상 App이 조정자 역할을 하는 것이 합리적입니다. 더 커지면 useTodos 같은 custom hook으로 로직을 분리할 수 있지만 지금은 추상화 비용이 더 큽니다.

외부 저장 데이터는 신뢰할 수 없고 React key 충돌이 실제 CRUD 오작동으로 이어질 수 있어 저장 경계에서 정규화합니다. UI 컴포넌트가 아닌 storage 모듈에 격리하면 복잡성이 다른 영역으로 퍼지지 않습니다.

CRUD의 책임은 state 변경이고 영속성은 state 변화에 반응하는 Effect 책임입니다. 저장 호출 누락을 막고 같은 상태 변화 경로를 한 곳에서 처리합니다.
